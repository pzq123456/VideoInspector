# VideoInspector 实时视频安全检测系统 —— 技术汇报

> 汇报人：项目负责人
> 时间：2026 年 8 月

---

## 一、项目概述

VideoInspector 是一套部署在 GPU 服务器上的**工业现场安全防护用品（PPE）实时视频检测系统**。系统接入多路 RTSP 摄像头（当前 6 路，移动布控球），对画面中的人员逐帧检测**安全帽、反光衣、安全带、吸烟**四类违规行为，命中后在满足连续帧确认与冷却策略的前提下，通过 Webhook 推送结构化告警（含违规对象坐标与实时渲染的证据帧）。

服务形态是常驻后台进程（Docker 容器部署），可同时对外提供带检测框标注的 RTSP 预览流，供安监中心或下游平台消费。当前已在实际网络摄像头上连续运行数日，累计触发并留存 140+ 条带证据帧的告警记录，端到端链路（解码 → 推理 → 判定 → 推送 → 消费端落盘）在真实环境下得到验证。

## 二、系统设计

### 2.1 技术选型

| 层次 | 选型 | 说明 |
|---|---|---|
| 推理框架 | NVIDIA DeepStream 9.0 + TensorRT | 工业级流式推理管线，GPU 硬解码/硬件缩放，动态 batch 批处理 |
| 模型 | Ultralytics YOLO26（n/s/m 三档） | 2026 年发布的最新 YOLO 系列，检测/分类任务同源 |
| 语言绑定 | Python + pyservicemaker | DeepStream 9.0 起官方废弃 pyds，改用官方推荐的 service-maker 绑定 |
| 部署 | Docker + docker-compose（CDI 挂载 GPU） | 一键起停，模型产物宿主机持久化，重启秒级恢复 |
| 告警出口 | HTTP Webhook（JSON + Base64 证据帧） | 协议解耦，下游平台自由对接 |

### 2.2 核心架构

采用**两阶段检测**设计，这是工业级 PPE 检测的主流做法，兼顾精度与算力：

```
RTSP×N ──> nvstreammux(batch=N) ──> person 整帧检测器（锚点）
                                    ├──> helmet 整帧检测器
                                    ├──> harness 二级分类器（作用在 person 框上）
                                    ├──> vest   二级分类器（作用在 person 框上）
                                    └──> smoke  二级检测器（作用在 person 框上）
    ──> 每路摄像头分别: nvdsosd 渲染 ──> tee ──> RTSP 预览流（单端口多挂载点）
                                              └──> appsink 证据帧缓存
```

关键设计决策：

1. **单配置文件为唯一事实来源**。模型拓扑、告警规则、摄像头列表全部声明在 `config.yaml`，启动时强校验、fail fast；新增/替换模型只需改配置，不改代码。
2. **每路摄像头、每条规则一套独立状态机**（`IDLE→ARMING→COOLDOWN`）。连续 N 帧确认防单帧误报，触发后冷却窗口防告警风暴，规则间互不干扰，可叠加。
3. **探针轻决策、重活异步卸载**。GStreamer 流线程内只做判定与上色；JPEG 编码走线程池，Base64/HTTP 推送走独立 daemon 线程 fire-and-forget，全程不阻塞推理管线。
4. **证据帧与预览流同源**。告警帧取自 nvdsosd 原生渲染后的画面，框与像素自洽，可直接作为责任认定的现场凭证。
5. **模型构建全自动**。`pt → onnx → TensorRT(fp16, 动态batch) → engine` 一键完成，带增量判定（跳过未变化的步骤）与环境指纹校验（GPU 型号/算力 + TRT 版本），产物可整目录删除重建。

### 2.3 告警数据契约

告警 payload 含 `alert_type`（区分违规类型）、`camera_id`、时间戳、违规对象列表（class/置信度/bbox/属性）与 Base64 证据帧，字段自解释、可扩展，适配各类下游接收端。

## 三、关键技术难点与攻关

以下问题均在真实环境下定位并解决，非演示性功能：

1. **DeepStream 9.0 迁移阵痛**。官方弃用 pyds 后无现成 Python 资料，我们从底层 C 结构体（`nvdsmeta.h`）和绑定的实际暴露字段入手，逐步摸清元数据层级，沉淀了一整套元数据探索工具与 464 行工程笔记。
2. **二级分类器"只挂 class0"的隐蔽缺陷**。实测发现 DeepStream 二级分类器仅挂载 labels 第 0 类的预测，第 1 类（恰是违规类）无论置信度多高都被静默丢弃，导致安全带违规告警完全失效。经抓取引擎原始 softmax、逐对象比对、OSD 渲染三重交叉验证后确认根因，最终通过**构建期自动交换输出通道、把违规类挪到 class0** 的方式根治，无需重训模型。
3. **分类器预处理脆弱性问题**。反光衣模型对输入缩放/补边极其敏感（同一画面，拉伸判"合规"、黑边 letterbox 判"违规"），排查定位到 nvinfer GPU 硬件缩放与训练时预处理不一致，穷尽配置旋钮无法根治，最终通过重训模型（加入部署侧预处理增强）解决。
4. **绑定层陷阱**。`object_items` 是一次性迭代器、部分字段取值会触发 C++ 层崩溃且无法用 Python 捕获，探针代码针对这些约束做了专门的防御性设计。
5. **工程环境一致性**。开发容器与生产镜像同源（同一 DeepStream 镜像），模型路径在启动时锚定为绝对路径，同一份配置在两端通用；容器入口做了环境诊断、CUDA 硬门禁与增量构建，避免"配置好了跑不起来"的部署事故。

## 五、技术潜力

- **架构可扩展**。当前拓扑已支持"整帧检测器 + 二级分类器 + 二级检测器"三类模型，新增违规类型（如吸烟已落地、其他行为）只需新增模型与规则配置；摄像头路数由动态 batch 支持，理论上可平滑扩容。
- **技术栈前沿**。DeepStream 9.0 + YOLO26 + TensorRT fp16 是当前 NVIDIA 生态下最新的推理组合，模型侧仍有明显提升空间（更大模型、更优预处理对齐）。
- **可产品化**。告警协议已标准化，具备接入监控大屏、微信/短信联动、跟第三方平台对接的基础；配置化设计使其从"单项目"走向"可交付方案"的成本较低。

## 六、市场对标与梯队定位

**结论：在"自研推理能力与工程化交付"维度上，本项目已达到市场先进梯队；但与成熟的商业化成套产品相比，在功能广度上仍有明确差距。**

对标分析：

| 维度 | 本项目 | 头部商业化产品（海康/大华等） |
|---|---|---|
| 推理引擎 | DeepStream + TensorRT fp16 | 同类（自研或 TensorRT 等价物） |
| 模型 | YOLO26 两阶段检测 | 同类（多为自研检测/跟踪模型） |
| 多路并发 | 6 路已验证，动态 batch 可扩容 | 数十~上百路级 |
| 告警与证据 | 独立状态机 + 证据帧，标准 Webhook | 同类能力 + 更成熟的管理平台 |
| 目标跟踪 | 未接入（无跨帧 ID 关联） | 标配（多目标跟踪、轨迹、逗留分析） |
| 平台化 | 无 Web UI/大屏/管理后台 | 标配 |
| 模型闭环 | 依赖人工训练/微调 | 部分具备数据回流与自动重训 |

说明：
- **达到先进梯队的部分**：两阶段检测架构、GPU 流式推理与工程化部署方式，与商业产品处于同一技术路线；同时解决了若干 DeepStream 9.0 新生态下社区尚未充分沉淀的底层难题（class0 挂载缺陷、预处理对齐），这些属于领先于多数自研团队的工作。
- **与成熟商用产品的主要差距**：一是**多目标跟踪**缺位（导致同一人跨帧的连续性只能靠规则阈值近似），二是**平台化**（管理后台、大屏、告警归档查询）尚未建设，三是规模化运维能力（集群、GPU 调度）待补。这些是"能用"与"产品级"之间的主要鸿沟。

## 七、不足与下一步

1. 引入 `nvtracker` 多目标跟踪，使告警从"帧级判定"升级为"目标级判定"，可显著降低误报并支持行为分析（越界、逗留）。
2. 建设模型训练/评估闭环，沉淀工地 PPE 数据集的持续积累与自动重训能力。
3. 补平台层：告警管理后台、大屏展示、历史回放检索。
4. 压测验证更大路数与更长无故障运行时间，补齐指标数据（单卡路数上限、帧率、告警延迟）。
